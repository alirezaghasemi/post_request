# Project: Build a Full-Featured Postman-Like API Development Platform Using Electron

## 1. Your Role

Act as a Principal Software Architect, Senior Electron Engineer, API Platform Engineer, Security Engineer, and QA Automation Lead.

Your mission is to design and build a production-grade desktop application that provides functional capabilities comparable to Postman.

This is a real software engineering project, not a UI mockup, prototype, or static dashboard.

The application must have working features, real protocol implementations, persistent storage, automated tests, import/export capabilities, and a maintainable architecture.

Do not attempt to implement everything in one uncontrolled coding pass.

**Mandatory rule: Work in explicit phases. Present the plan for each phase and wait for my approval before starting that phase.**

Do not proceed to the next phase without my explicit approval.

My approval of a phase means that you may implement that phase only. It does not authorize you to start subsequent phases automatically.

---

## 2. Core Objective

Build an independent desktop application inspired by the functional capabilities of Postman.

The application must:

- Run on Linux, Windows, and macOS.
- Be built with Electron.
- Work offline for all local features that do not inherently require external services.
- Provide a professional, developer-focused user interface.
- Support HTTP API development, request execution, response inspection, automated testing, scripting, collections, environments, API specifications, mocking, and automation.
- Be modular and extensible so new protocols and features can be added without rewriting the core.
- Prefer local-first storage and privacy.
- Avoid mandatory user registration or cloud accounts for core functionality.
- Import and export supported Postman-compatible data formats wherever technically possible.
- Provide transparent capability labels for fully implemented, partially implemented, externally dependent, and unavailable features.

Do not claim complete Postman compatibility unless it has been verified through actual feature-level testing.

Do not copy Postman's proprietary source code, branding, logos, or protected assets. Create an original product identity and interface.

Working title: **DevPilot API Studio**.

The product name must be configurable.

## 3. Mandatory Engineering Principles

Follow these principles throughout the project:

1. Build actual functionality, not placeholder buttons.
2. Never simulate successful API responses when a real request is expected.
3. Never silently ignore unsupported protocols or authentication methods.
4. Never return fake success messages for unfinished operations.
5. Never mark a feature complete without implementing and testing its acceptance criteria.
6. Avoid giant components, monolithic services, and unnecessary abstractions.
7. Separate the Electron main process, preload layer, renderer, protocol engines, persistence, scripting engine, and automation engine.
8. Use strict TypeScript.
9. Use dependency injection where it improves testability and modularity.
10. Define interfaces for protocol adapters, persistence, authentication providers, importers, exporters, and automation runners.
11. Use structured errors and consistent logging.
12. Write unit tests, integration tests, and end-to-end tests.
13. Document architectural decisions.
14. Keep dependencies maintained and compatible with the selected Electron version.
15. Never downgrade security settings merely to make a feature work.
16. Do not add unnecessary external services or subscriptions.
17. Do not introduce a backend server unless a feature genuinely requires one.
18. Do not use Docker as a mandatory dependency for the desktop application.
19. Do not overwrite existing project files without inspecting them first.
20. Do not delete working features to simplify implementation.

When a requirement is ambiguous, identify the ambiguity and propose a concrete solution before implementation.

When a feature is technically infeasible or depends on a proprietary service, explain the limitation and propose a practical alternative.

## 5. Application Architecture

Design the application around independently testable modules.

Use the following logical architecture:

### A. Electron Main Process

Responsible for:

- Application lifecycle.
- Window management.
- File dialogs.
- Native filesystem access.
- Secure persistence.
- Native notifications.
- IPC routing.
- Application updates, when configured.
- Process management.
- Restricted access to operating-system functionality.

### B. Preload Layer

Expose only explicitly authorized capabilities through contextBridge.

Every IPC handler must validate:

- The sender.
- Input types.
- Payload size.
- File paths.
- Permissions.
- The requested operation.

Do not expose raw Node.js APIs to the renderer.

### C. Renderer

Responsible for:

- User interface.
- Editors.
- Request builder.
- Collection explorer.
- Response viewer.
- Test results.
- Environment selection.
- Workspace management.
- Settings.
- Documentation.
- Visual workflow editor.

The renderer must not directly access the database or unrestricted filesystem.

### D. Core Domain Layer

Define domain models and interfaces for:

- Requests.
- Responses.
- Collections.
- Folders.
- Variables.
- Environments.
- Authentication.
- Protocols.
- Test cases.
- Execution results.
- API specifications.
- Mock examples.
- Workflows.

Keep domain logic independent from React components.

### E. Protocol Engine

Provide separate adapters for each supported protocol.

Each adapter must declare:

- Supported features.
- Authentication support.
- Streaming support.
- Cancellation behavior.
- Connection lifecycle.
- Known limitations.
- Test coverage.

### F. Script Engine

Run user scripts in a restricted execution environment.

Separate pre-request scripts, post-response scripts, and assertions.

Do not execute arbitrary user scripts in the Electron main process.

### G. Persistence Layer

Provide repositories, migrations, transaction handling, backup, restore, and import/export services.

### H. Automation Engine

Provide Collection execution, data-driven tests, workflow execution, scheduled tasks where supported, and command-line integration.

Produce a Mermaid architecture diagram and document the data flow before implementation.

- nodeIntegration disabled in renderers.

- Restrictive Content Security Policy.

- Restricted navigation.
- Restricted new-window creation.

- No unrestricted filesystem API exposure.
- No secrets in logs.

- Secure updates.

8. Update documentation.
